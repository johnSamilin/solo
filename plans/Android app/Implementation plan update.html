Updated implementation plan for the Solo mobile app for Android

Changes per the user's requirements

1. Removal of the dark theme

  • Change: Dark theme support has been removed from the implementation plan
  • Reason: The user does not need a dark theme; minimalism is what matters
  • Impact on the plan:
    • Remove the item "Configure the app theme (light/dark mode)" from section 2.1
    • Remove theme settings from the settings screen (section 5.3)
    • Use only the light theme in the app

2. Dropping image compression

  • Change: Image compression on upload has been removed
  • Reason: It is important to preserve image quality unchanged
  • Impact on the plan:
    • Remove the item "Add image compression for optimization" from section 4.3
    • Change the uploadImage method to preserve original quality
    • Increase memory limits to handle large images

3. Storing data in an arbitrary folder with elevated permissions

  • Change: Notes and images are stored in a rootFolder that can be located anywhere in the file system
  • Reason: Flexibility in choosing the data storage location
  • Impact on the plan:
    • Add the MANAGE_EXTERNAL_STORAGE permission request to AndroidManifest.xml
    • Implement folder selection via the Storage Access Framework with support for any location
    • Update FileSystemManager to work with arbitrary paths
    • Add a security check for arbitrary paths

4. Removal of native UI components (item 5.1)

  • Change: The implementation of native UI components has been removed
  • Reason: The web app already has the required UI; minimalism is what matters
  • Impact on the plan:
    • Remove the entire section 5.1 "Native UI components"
    • Simplify MainActivity to a basic WebView container
    • Remove Navigation Drawer, Search Bar, FAB, Bottom Navigation
    • Keep only minimal navigation for folder selection and settings

5. Creating a new nativeBridge.ts (electron.ts stays)

  • Change: A new file nativeBridge.ts with the getPlatformAPI() abstraction is created; electron.ts remains unchanged
  • Reason: We don't break the Electron client and add a common abstraction for both platforms
  • Impact on the plan:
    • Create src/utils/nativeBridge.ts with getPlatformAPI() and getNativeAPI()
    • Update stores to use nativeBridge where cross-platform support is needed
    • electron.ts keeps working as-is for Electron-specific calls

6. Publishing not only to Google Play, but also to RuStore

  • Change: Added support for publishing to an alternative app store
  • Reason: Expanding the app's audience
  • Impact on the plan:
    • Add build preparation for RuStore
    • Configure the store's specific requirements
    • Update section 7.2 "Build and publishing"

7. Removal of analytics and monitoring

  • Change: Analytics and crash reporting have been removed
  • Reason: The user does not need analytics or monitoring
  • Impact on the plan:
    • Remove the item "Implement analytics and crash reporting" from section 7.1
    • Remove the corresponding dependencies from Gradle
    • Simplify the app's code

Updated bridge architecture

Key architectural decisions (agreed)

  1. All @JavascriptInterface methods return JSON strings -- the Android bridge is synchronous, the JS side parses the JSON
  2. Async operations (selectFolder) use the callback pattern -- the Bridge calls evaluateJavascript() with the result after the Activity completes
  3. SAF (DocumentFile) is the primary approach to the file system for Google Play compatibility. MANAGE_EXTERNAL_STORAGE -- only for RuStore via product flavors
  4. nativeBridge.ts is a new file, electron.ts remains unchanged, without breaking the Electron client
  5. The Kotlin SearchEngine implements the same API contract search(query, tags) as Electron
  6. The typewriter sound is played natively via AudioPlayer (not via a WebView URL)

WebViewBridge.kt (updated structure)

class WebViewBridge(
    private val activity: MainActivity,
    private val fileSystemManager: FileSystemManager,
    private val audioPlayer: AudioPlayer,
    private val searchEngine: SearchEngine
) {
    // Async: launches SAF picker, calls JS callback via evaluateJavascript()
    @JavascriptInterface
    fun selectFolder() {
        activity.runOnUiThread { activity.launchFolderPicker() }
    }

    @JavascriptInterface
    fun getDataFolder(): String {
        // Returns JSON: {"success":true,"path":"/storage/..."}
        return fileSystemManager.getDataFolderJson()
    }

    @JavascriptInterface
    fun openFile(relativePath: String): String {
        // Returns JSON: {"success":true,"content":"..."}
        return fileSystemManager.openFileJson(relativePath)
    }

    @JavascriptInterface
    fun updateFile(relativePath: String, content: String): String {
        // Returns JSON: {"success":true}
        return fileSystemManager.updateFileJson(relativePath, content)
    }

    @JavascriptInterface
    fun readStructure(): String {
        // Returns JSON: {"success":true,"structure":[...]}
        return fileSystemManager.readStructureJson()
    }

    @JavascriptInterface
    fun updateMetadata(relativePath: String, metadataJson: String): String {
        return fileSystemManager.updateMetadataJson(relativePath, metadataJson)
    }

    @JavascriptInterface
    fun scanAllTags(): String {
        return fileSystemManager.scanAllTagsJson()
    }

    @JavascriptInterface
    fun createNote(parentPath: String, name: String): String {
        return fileSystemManager.createNoteJson(parentPath, name)
    }

    @JavascriptInterface
    fun createNotebook(parentPath: String, name: String): String {
        return fileSystemManager.createNotebookJson(parentPath, name)
    }

    @JavascriptInterface
    fun deleteNote(relativePath: String): String {
        return fileSystemManager.deleteNoteJson(relativePath)
    }

    @JavascriptInterface
    fun deleteNotebook(relativePath: String): String {
        return fileSystemManager.deleteNotebookJson(relativePath)
    }

    @JavascriptInterface
    fun renameNote(relativePath: String, newName: String): String {
        return fileSystemManager.renameNoteJson(relativePath, newName)
    }

    @JavascriptInterface
    fun renameNotebook(relativePath: String, newName: String): String {
        return fileSystemManager.renameNotebookJson(relativePath, newName)
    }

    @JavascriptInterface
    fun playTypewriterSound() {
        audioPlayer.play()
    }

    @JavascriptInterface
    fun uploadImage(base64Data: String, fileName: String): String {
        // Returns JSON: {"success":true,"url":"assets/..."}
        return fileSystemManager.saveImageJson(base64Data, fileName)
    }

    @JavascriptInterface
    fun search(query: String, tagsJson: String): String {
        // Returns JSON: {"success":true,"results":[...]}
        return searchEngine.searchJson(query, tagsJson)
    }

    @JavascriptInterface
    fun toggleZenMode(enable: Boolean): String {
        return """{"success":true,"isZenMode":$enable}"""
    }
}

Integration with the web app

  1. New file src/utils/nativeBridge.ts (electron.ts stays as-is):

    • getNativeAPI() -- returns window.electronAPI or the Android wrapper
    • The Android wrapper parses JSON strings from window.SoloBridge into Promise objects compatible with ElectronAPI
    • selectFolder() on Android uses a callback via evaluateJavascript()

  2. Typewriter sound -- on Android it is played natively via window.SoloBridge.playTypewriterSound(), Howler.js is not used

Risks and mitigations

Risk Mitigation
The MANAGE_EXTERNAL_STORAGE permission may be rejected by Google Play Use the Storage Access Framework as a fallback, prepare a justification for Google Play
WebView performance on older devices Caching, load optimization
Android file system limitations with arbitrary paths Thorough testing on different Android versions
Path traversal security with arbitrary root folders Strict canonical path validation, isolation of operations
Memory consumption by large uncompressed images Progressive loading, lazy loading of images
