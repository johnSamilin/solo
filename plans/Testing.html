Solo — Playwright Test Case Specification

Status: design document (no automation code exists yet — the previous ad-hoc suite was removed). This document is the single source of truth for what the future Playwright suite must cover, how it must be structured, and which real bugs (GitHub issues) each case protects against.

Core principle: we test the REAL application. The primary suite drives the actual Electron app (real main process, real IPC handlers, real preload bridge, real filesystem) via Playwright's Electron support. No mocking of window.electronAPI: the historical bugs (#33 file not moved, #34 symlinks, #17 logs, #28 empty saves) lived in the Electron layer, and any mock of it would be blind to exactly those regressions.

Sources of inspiration: all open and closed issues in https://github.com/johnSamilin/solo/issues (issues #46–#61 are excluded — they are known to be erroneous).

1. Goals and principles

  1. Every closed bug must have a regression case. If an issue was fixed, the suite must contain a case that fails when the bug is reintroduced.
  2. Verify the data on the real disk. Solo's contract is "your notes are plain HTML + JSON metadata in your filesystem". The primary assertion mechanism is a workspace snapshot comparison: a real fixture directory is seeded on disk → user manipulations through the real UI → the final directory tree is read back and diffed against a golden expected state. This catches silent corruption (#28 emptied notes, #84 dropped sourceUrl, #33 un-moved files, #19 stale paragraphTags) that no UI assertion would see.
  3. Deterministic fixtures. Each scenario starts from a versioned fixture workspace copied into a fresh temp data folder, never from leftovers of a previous test. One app instance per test (or per isolated group), launched against its own temp userData + dataFolder.
  4. Real services where feasible, controlled boundaries where not. The only things stubbed are external boundaries the test must control: the network for read-later (a local HTTP fixture server instead of live sites) and native OS dialogs (env-guarded test hooks, §2.5). The semantic-search binary is the real Go build (SOLO_SEARCH_BIN); digiKam tests use a real digikam4.db fixture.
  5. Feature-flag matrix. Features are gated by feature-flags.json per platform (PACKAGED / DESKTOP / MOBILE). The Electron suite runs the DESKTOP profile. The PACKAGED profile (web demo, deep linking) is tested as a second Playwright project in a real browser against PLATFORM=packaged npm run dev — its stub API (src/utils/createStubAPI.ts) is the production implementation for web, not a test mock.
  6. Honest scope. Android-native behavior (system file pickers, share sheet, selection handles, widget) cannot be driven by Playwright on desktop. Those items are listed in §7 as manual/device tests, not silently "covered".
  7. The plans/ folder is the mock workspace — documentation and fixtures at once. Instead of maintaining separate fake data, the suite points the app at a copy of the repo's own plans/ folder: real Solo notes (HTML + JSON sidecars) containing tables, code blocks, tags and long cross-referenced text. Every doc case doubles as a dogfooding check that the app can open, edit and save its own documentation without loss. The smaller fixtures in §5 remain only for states that cannot be expressed as documentation (empty notes, symlinks, oversized workspaces).

2. Test architecture (for the future implementation)

2.1 Launching the real app

Two Playwright projects:

Project electron (primary). Uses _electron.launch() from @playwright/test:

const app = await _electron.launch({
  args: ['native-clients/electron'],          // package.json "main": electron/dist/main.js
  cwd: repoRoot,
  env: {
    ...process.env,
    NODE_ENV: 'development',                  // renderer loads vite dev server (webServer in config)
    SOLO_NO_DEVTOOLS: '1',                    // test hook (§2.5)
    SOLO_DATA_DIR: tempDataDir,               // test hook: pre-seeded fixture workspace (§2.5)
    SOLO_USER_DATA_DIR: tempUserDataDir,      // test hook: isolated settings.json/logs (§2.5)
    SOLO_SEARCH_BIN: goBinaryPath,            // already supported by main.ts (optional)
    SOLO_SEARCH_MODEL_DIR: modelDir,          // already supported by main.ts (optional)
  },
});
const page = await app.firstWindow();
  • The renderer runs from the vite dev server (fast iteration, source maps) while the main process, preload, IPC handlers, protocols (voice://, video://), logger and filesystem code are the real production code.
  • A second, slower electron:packaged suite (optional, run on release branches) launches the electron-forge package output to verify the shipped artifact (process.resourcesPath/dist code path, auto-update disabled).
  • Media recording tests pass Chromium switches through launch args: --use-fake-device-for-media-stream, --use-fake-ui-for-media-stream, --autoplay-policy=no-user-gesture-required.

Project web-packaged. Plain Chromium against PLATFORM=packaged npm run dev (the published github.io demo build). Covers deep linking (DL-*), theme rendering, and anything specific to the PACKAGED flag profile.

2.2 Per-test isolation

Each test gets:

  • a fresh temp dataFolder (fixture copied from tests/fixtures/workspaces/<name>/, with plans/ — the repo's own documentation folder — as the primary workspace, see §1.7 and §5),
  • a fresh temp Electron userData dir (settings.json, logs),
  • its own launched app instance; teardown closes the app and keeps the temp dir only on failure (attached to the Playwright report as an artifact — the actual corrupted workspace is the best debugging evidence).

Tests within a file may share one seeded app instance only when they are read-only (search, statistics, themes); anything that writes gets a fresh instance.

2.3 Feature flags

The Electron app is the DESKTOP profile. Flag-gated behavior is asserted per profile: cases that must NOT exist under a profile (e.g. export UI under PACKAGED) run in the web-packaged project. MOBILE-specific flows are manual (§7).

2.5 Required test hooks in electron/main.ts (small, env-guarded, zero prod impact)

To automate the real app without fighting native OS dialogs, main.ts needs a few minimal hooks (each active only when the corresponding env var is set):

Hook Purpose Replaces
SOLO_DATA_DIR Use this folder as dataFolder at startup (skip/override settings.json) dialog.showOpenDialog for folder selection
SOLO_USER_DATA_DIR app.setPath('userData', …) before anything reads it polluting the developer's real userData
SOLO_E2E_EXPORT_DIR exportFile writes into this dir with the suggested file name instead of showing dialog.showSaveDialog native save dialog (untestable)
SOLO_E2E_PICK_FILE selectFile returns the pre-set path(s) native open dialogs (image pick, cover pick, digiKam db pick)
SOLO_NO_DEVTOOLS Don't auto-open DevTools in development mode flaky focus/screenshot noise

These are test hooks, not mocks: all real logic (path validation, write-rename-tmp, logging) still executes.

2.6 Network boundary for read-later

fetchUrl runs in the main process, so page.route() cannot intercept it. Instead the suite starts a local HTTP fixture server (tests/fixtures/http/) serving recorded article HTML (a couple of representative pages: heavy chrome/ads, clean article, page with <img>/<audio>), and read-later cases use http://127.0.0.1:<port>/… URLs. This also makes RL cases deterministic and offline-safe.

3. Snapshot-based verification (core mechanism)

3.1 Idea

Each data-integrity scenario is a triple:

(initial fixture directory, manipulation script through the real UI, expected final directory)

The harness:

  1. workspace.seed(fixture) — copies the fixture tree into the temp dataFolder before app launch.
  2. The test performs user-level manipulations via page objects against the real app.
  3. Trigger a save/settle point (switch note, close modal, or explicit wait for the IPC call to land — assert via UI feedback like toast/sidebar state, not sleeps).
  4. workspace.dump(dataFolder) — walks the real directory and serializes it to canonical JSON.
  5. Assertion: expect(dump).toEqual(expectedDump) where the expected dump is generated from the golden directory <fixture>.<scenario>.expected/.

Because the dump reads the real disk, it verifies the entire stack: renderer logic → preload → IPC handler → fs. A golden-file change in a PR is a red flag requiring explicit human approval — that is exactly how silent-corruption regressions (#28, #84) get caught in review.

3.2 Dump format & normalization

Dump shape: { [relativePath]: { type: 'folder'|'file'|'symlink', target?, html?, metadata? } } (.json sidecars are parsed into metadata, .html kept as text, other files as { size, sha256 } — covers images/audio/video without golden-file bloat).

Normalization rules:

Volatile data Rule
createdAt / updatedAt in metadata Pre-seeded fixture files keep their fixed timestamps (they come from disk). For notes created during a test, replace timestamp values with the placeholder "<TS>". Cases asserting time relations (timeline order) compare relative order, not values.
Generated note id Replace with "<ID>" placeholder unless the case is about ids (RL-01/#79).
Absolute paths leaking into files (e.g. outputPath, digiKam db path) Temp-dir prefix replaced with <DATA> / <TMP>.
JSON key order, directory order Sorted canonically.
HTML whitespace Compare strictly (only CRLF→LF). Strictness is what catches #28.
Binary assets sha256 + size (catches "asset copied to wrong folder / truncated").

3.3 When NOT to snapshot

Pure UI/visual behavior (zen mode, themes, typography, counters) is asserted with DOM/CSS assertions. Some cases assert both (tag rename: UI shows the new name and the workspace diff shows metadata rewritten everywhere).

4. Test case catalog

Priorities: P0 — data integrity / core flow, must always pass; P1 — major features; P2 — nice-to-have, edge cases. Snapshot: — case ends with a workspace diff. Default project: electron (DESKTOP profile); web = web-packaged project.

The primary fixture is the repo's own plans/ folder — it is documentation and mock data at the same time (§1.7): a suite run copies plans/ into the temp dataFolder, so the app is exercised on real, richly formatted notes (tables, code blocks, tags, sidecar metadata). Additional small fixtures live under tests/fixtures/workspaces/ and cover only states that documentation cannot express. Minimal set required by the catalog:

8. Suggested implementation order

  1. Harness first: env-guarded test hooks in main.ts (§2.5) + launch/isolation helper (§2.1–2.2) + workspace seed/dump/diff over real directories (§3) + basic/ fixture + WS-02 (fresh-start flow, end-to-end through the real app) + WS-09 (docs round-trip against plans/ — doubles as the harness self-check).
  2. P0 data-integrity batch: NOTE-01/02/04/06, TAG-02/03/05/06, MOVE-01, ZEN-02, RL-01/04, SEARCH-03 — covers the worst historical bugs (#28, #73, #26, #19, #29, #84, #33, #76, #79, #24).
  3. P1 features: SEARCH-01/02/04/05/06/09, WS-01/04/05/06/07, RL-02/06, EXP-01/02, HL-01/02, ASSET-01/02/07, NOTE-03/05/08/09/10/12/13, TAG-01/04/07, LOG-01, THEME-02/03, ZEN-01.
  4. P2 long tail + PERF budgets (baselines measured on CI hardware first) + SEARCH-08 (gated on the Go binary artifact) + ASSET-08 (digiKam fixture) + web-packaged DL-* suite.
  5. Release smoke (electron:packaged project): WS-02 + NOTE-01 + EXP-01 against the forge-packaged artifact before each release.
